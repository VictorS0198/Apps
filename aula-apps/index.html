Apps para Android y Windows

Continuación de Aula de Código. Ya sabes cómo funciona un HTML: un archivo que el navegador lee. Aquí ves qué cambia cuando una app se compila para un teléfono o para Windows: proyectos de muchos archivos, lenguajes distintos, y cómo elegir y portar entre ellos.

Conceptos

De un archivo a un proyecto

Una app nativa no se “abre”: se construye. Elige una plataforma y sigue el camino del código desde que lo escribes hasta que corre. Haz clic en cada etapa.

¿Por qué ya no es un solo archivo?

1. Separar responsabilidades

Pantallas, lógica, datos y estilos en archivos distintos. Lo que en tu HTML son secciones (<style>, <script>), aquí son archivos y carpetas.

2. Recursos por variante

Íconos para cada densidad de pantalla, textos por idioma, temas claro/oscuro. El sistema elige el archivo correcto según el dispositivo.

3. Configuración de construcción

El compilador necesita saber versión mínima, permisos, librerías, firma. Eso vive en archivos como build.gradle.kts o .csproj.

4. Dependencias descargadas

En HTML pegas un <script src>. Aquí declaras librerías y un gestor (Gradle, NuGet, npm, cargo) las descarga.

5. Código generado

Carpetas build/, bin/, obj/, node_modules/ las crea la herramienta. No se editan ni se suben a Git.

6. Pruebas automáticas

Carpetas test/ con código que revisa tu código. Opcional para apps personales, pero ya viene en la plantilla.

Conceptos

Compilar vs interpretar

El procesador solo entiende código máquina (números). Cada lenguaje llega ahí por un camino distinto: unos se traducen antes (compilados), otros mientras corren (interpretados), y muchos hacen un poco de cada uno.

← Más flexible, cambias y corres al instanteMás rápido y optimizado, pero hay que compilar →

Las palabras clave

Compilador

Programa que traduce tu código fuente a otra forma (bytecode o código máquina) antes de ejecutarlo. Ej: kotlinc, Roslyn (C#), rustc.

Bytecode / IL

Código “intermedio”: ya no es texto, pero tampoco es de un procesador específico. Por eso un mismo APK corre en celulares con chips distintos.

JIT (Just-In-Time)

Traduce a código máquina mientras la app corre, las partes que más se usan. Lo hace el motor de JavaScript de Edge y el CLR de .NET.

AOT (Ahead-Of-Time)

Traduce todo a código máquina antes. Arranque más rápido. Android lo hace al instalar/optimizar; Flutter, Rust y C++ lo hacen al compilar.

HTML + JS lo que ya conoces

Kotlin + Compose Android moderno

La idea es la misma que ya aprendiste: estado → la pantalla se dibuja a partir del estado. En Compose no llamas render(): cuando cambia un mutableStateOf, Compose vuelve a ejecutar (“recompone”) solo las funciones que lo leen.

Antes de Compose: XML + Views

Hasta ~2021 las pantallas se dibujaban en archivos XML (res/layout/activity_main.xml) y el código Kotlin/Java las buscaba con findViewById, muy parecido a document.getElementById. Todavía verás tutoriales así; Google recomienda Compose para apps nuevas.

Arquitectura recomendada: capas y flujo de datos

En tu HTML todo vive en un archivo: estado, render, guardar. En Android se separa en capas, cada una con un trabajo. Elige un escenario para ver el recorrido, o haz clic en una capa.

Regla de oro (la misma de siempre): los datos bajan como estado (ViewModel → UI) y las acciones suben como eventos (UI → ViewModel). Se llama flujo unidireccional de datos.

XAML y binding vs HTML

XAML es el “HTML de Windows” (WPF, WinUI, MAUI). La gran diferencia: el binding conecta la pantalla con los datos automáticamente, sin render(). Pasa el mouse por la tabla o las líneas.

Portabilidad: llevar una app a otra plataforma

Una app tiene 4 capas, y no todas se mudan igual. Este es el mapa para llevar tus apps HTML a Android y Windows.

Las 4 capas y qué tan portables son

DatosJSON, CSV, SQLite, Supabase

Lo más portable: cualquier lenguaje los lee. Cuídalos y todo lo demás se puede rehacer.

Lógicacálculos, reglas, validaciones

Se traduce casi línea por línea (ver Piedra Rosetta).

Interfazpantallas, botones, estilos

Cada framework tiene su forma: normalmente se reescribe.

Sistemacámara, archivos, notificaciones

Específico de cada plataforma: siempre cambia.

Rutas desde tus apps HTML

Tu preferencia por HTML es una buena estrategia de portabilidad: con PWA, Capacitor o Tauri el mismo código llega a Android y Windows. Lo que no debes perder nunca es el formato de los datos: mientras sea JSON/CSV/SQLite compatible, cualquier app futura (en cualquier lenguaje) puede leerlos.
